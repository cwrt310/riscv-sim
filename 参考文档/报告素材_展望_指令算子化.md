# 报告素材：展望与优化方向

> 定位：课程报告"展望"章节的素材。从指令算子化、表驱动扩展谈起，延伸出编译器前端、伪指令与标签、OS 支持、可视化等演进方向。

---

## 一、现状：集中式分派的问题

当前版本的模拟器在指令执行部分采用集中式分派结构：所有指令的执行逻辑汇聚于一个基于操作码（opcode）的 switch 分支中。该结构直观、易读，适合教学与实现阶段；但从开源项目与可持续演进的角度看，它存在一个明显的不足——任何指令的新增或修改都必须触及同一分支函数，在多人协作场景下容易产生合并冲突，也不符合"对扩展开放、对修改关闭"的开闭原则。

## 二、方向 1：指令算子化与表驱动（CPU 侧）

后续演进计划引入**算子化的指令扩展机制**。该思路借鉴自 buckyball 项目中的 ball 抽象：在 buckyball 中，每个 ball 是一个具有标准接口的算子单元，通过替换与叠加 ball 即可组装出不同的加速器配置；类比到本模拟器，我们同样将"一条指令"视为一个标准算子单元，为其规定统一的处理函数签名，并以操作码为索引、将所有算子组织为一张**分派表**。核心执行函数不再承载具体执行逻辑，而简化为"查表、调用"一个动作：

```cpp
using Handler = void(*)(CPU&, u32);   // 标准算子接口（类比 ball 的标准接口）
Handler dispatch[128];                // 分派表（类比 ball 的插槽）
dispatch[opcode](cpu, inst);          // 核心执行 = 查表 + 调用
```

该重构完成后，新增一条指令将从"修改核心分支代码"变为"新增一个算子函数并登记一条表项"，核心执行逻辑不因指令增加而改动；不同贡献者的开发工作在文件层面相互隔离，显著降低协作成本。同时，表驱动结构也为后续通过配置文件加载指令、动态注册扩展等能力奠定了基础。

## 三、方向 2：汇编器表驱动

"表驱动"不仅适用于指令执行（CPU 侧），同样适用于指令翻译（汇编器侧）。当前汇编器在 `assembleLine` 中以一连串 `if (mnemonic == "addi")` / `if (mnemonic == "andi")` 的硬编码分支逐条翻译指令，每条指令的 funct3、funct7、opcode 等编码信息被"写死"在各自的 if 块中，面临同样的扩展难题。表驱动的做法，是把"指令名 → 编码信息"的对应关系抽出为一张**指令描述表**：

```cpp
struct InsnDesc { u32 opcode; int funct3; int funct7; char type; };
std::unordered_map<std::string, InsnDesc> insn_table = {
    {"addi", {Op::OP_IMM, 0, 0,   'I'}},
    {"andi", {Op::OP_IMM, 7, 0,   'I'}},
    {"add",  {Op::OP,     0, 0,   'R'}},
    {"sub",  {Op::OP,     0, 0x20,'R'}},
    // ...
};
```

这样"新增一条指令"就从"改 if-else 逻辑"变为"往表里加一行数据"，与 CPU 侧的算子化分派表形成同构。二者共同的本质正是**表驱动：把"逻辑"变成"数据"，代码只负责"查表照做"**——改数据永远比改代码安全、简单、不冲突。

## 四、方向 3：编译器前端（迷你语言）

另一个纵向的演进方向，是为模拟器增加一个**编译器前端**，使程序入口从"手写汇编"上移至"高级表达式乃至迷你语言"。当前模拟器的输入是汇编文本，用户需手动管理寄存器与编码；若在汇编器之上再构建一个轻量级的编译前端，接受形如 `3-(5-2)` 的算术表达式并自动生成对应的 RISC-V 指令序列，即可将"读懂表达式 → 生成指令"这一原本手动的过程自动化。由于模拟器已具备完整的汇编器与执行器，该前端只需补足"词法分析、语法分析、代码生成"三步，其中代码生成所依赖的指令编码知识恰是本项目已经掌握的部分，因此实现成本显著低于从零构建一个完整编译器。

该方向可分层推进：首先支持算术表达式（数字、四则运算、括号），其次引入变量与赋值以建立符号表，最后利用已实现的分支指令生成 `if`/`while` 等控制流，使前端逐步成长为面向本模拟器的一门迷你编程语言。与工业级编译器相比，这一前端通过限定语言子集、省略类型系统与代码优化，将复杂度控制在教学项目可及的范围内，同时保留了编译器的核心骨架，为后续深入理解 MLIR、LLVM 等真实编译框架（如 buckyball 所使用的 buddy-mlir）提供了一条从"会生成机器码"到"理解编译全貌"的进阶路径。

## 五、方向 4：伪指令与标签支持

另一个可选的演进方向，是为汇编器增加**伪指令与标签支持**。当前汇编器仅支持"一文字一指令"的直接翻译，每条指令的立即数与跳转偏移量都需由程序员手动计算并写死。伪指令（如 `mv`、`li`、`j`、`nop`、`not`、`neg`、`beqz` 等）是围绕"x0 恒为 0、写入被丢弃"这一特性定义的简写形式，由汇编器自动展开为一条或多条真实指令；而标签（label）支持则要求汇编器采用"两遍扫描"——第一遍收集所有标签及其地址，第二遍在翻译时把标签引用解析为相对偏移量。二者共同将程序员从"手算偏移量、手写冗长指令"中解放出来，是汇编器从"玩具"走向"可用"的关键一步，也为后续的编译器前端提供了必要的底层支撑。

## 六、方向 5：运行操作系统

另一个重要的演进方向，是让模拟器具备**运行操作系统的能力**。操作系统本身也是一个程序，但它依赖硬件提供三项普通程序所不需要的能力：**特权级**（区分操作系统与用户程序的权限）、**陷阱机制**（发生异常或系统调用时，CPU 能跳转到操作系统指定的处理程序）、**设备抽象**（如通过内存映射 I/O 访问 UART 串口）。为此，模拟器需补全基础指令集（RV32I 与 M 扩展）、实现特权指令（`ecall`/`mret` 及 CSR 读写指令）、引入控制状态寄存器（`mtvec`/`mepc`/`mcause` 等）与陷阱处理流程，并提供一个最小化的 UART 设备。完成这些后，即可在模拟器上运行一个最小操作系统（启动 → 串口输出 → 处理系统调用 → 上下文切换），该方向可参考南京大学 PA 的 nanos-lite 等教学 OS。这一演进与 buckyball 的宿主核（Rocket 运行 Linux）高度呼应——CSR、陷阱与 UART 正是 Rocket 支撑 Linux 的底层机制，因此该方向不仅提升了模拟器的能力边界，也为理解 buckyball 的宿主侧硬件铺平了道路。

## 七、方向 6：数据通路图与流水线动画（Qt）

另一个提升项目展示与教学价值的方向，是为 Qt 界面增加**数据通路图与流水线动画**。当前规划的界面以「显示 + 控制」为主——用表格控件显示寄存器与内存、用按钮控制单步与运行，已足以支撑功能演示；但 CPU 执行一条指令的过程（取指、译码、执行、访存、写回）本质上是一连串「看不见」的内部状态流转，仅靠一张静态的寄存器表，观察者难以直观理解「这条指令在 CPU 里到底经历了什么」。为此，可在界面层引入 Qt 的 `QPainter` / `QGraphicsView` 自绘能力：将数据通路（寄存器堆、ALU、内存、PC 及各控制信号连线）绘制为一幅结构图，并在单步执行时高亮当前活跃的部件与数据流向；更进一步，可将取指-译码-执行等阶段组织为流水线时序示意，让多条指令在各级流水中的「流动」以动画呈现。这一可视化与前述的算子化分派表形成呼应——分派表让「每条指令做什么」可查，可视化让「执行时发生了什么」可见。需要强调的是，该方向属于**加分项**：基础界面用现成控件即可完成，自绘动画应在功能跑通、时间有余时再投入，不宜喧宾夺主。

## 八、结语：结构、测试、文档三位一体

我们认为：**结构决定"能不能改"，测试决定"敢不敢改"，文档决定"会不会改"。** 因此在推进算子化的同时，项目将配套建设基于真值表的回归测试集与对拍官方 Spike 模拟器的自动化验证，并编写说明"如何新增一条指令"的贡献指南（CONTRIBUTING）文档，从结构、验证、文档三个层面共同保障开源后的可维护性与社区友好度。
