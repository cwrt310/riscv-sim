## 三、⚠️ 顺序红线（最重要的一条）

**组长先把两张表骨架做完并合入 main，队友再开始补指令。** 原因：

- 骨架合入前，加指令还是"改 `execute()` 的 switch / 插 if 链"——三个人同时改这两个函数，git 冲突爆炸；
- 骨架合入后，加指令变成"表里加行 + 独立算子函数"，**文件层面互不干扰**，并行才安全。

时间安排：组长 ①（半天）→ 组长 ②（半天到一天）→ 本周内队友并行开工。

## 四、加指令的新套路（所有人必读，取代旧套路）

**表驱动之后，加一条指令不再是"改两个函数的逻辑"，而是"加数据 + 加独立代码"**：

1. **汇编器**：往 `Assembler.cpp` 的 `insn_table` 加**一行**（如果是新格式，还要在编码器 switch 加分支）：
   ```cpp
   {"blt", {Op::BRANCH, 4, 0, 'B'}},   // 一行 = 一条指令
   ```
2. **CPU**：写一个算子函数（或往对应 opcode 的算子函数里加一个 case），在 `initDispatch()` 登记：
   ```cpp
   dispatch[Op::BRANCH] = exec_branch;   // 已有登记的话，只需改 exec_branch 内部
   ```
3. **测试**：往 `tests/` 加用例（参考《测试手册》格式，预期值先用手算）。

**每改一步就跑 `tests/` 回归**——4 个测试全过才 push。

> 详细语法见《表驱动入门_从函数指针到哈希表.md》，施工图见《表驱动改造实战_riscv-sim版.md》。

## 五、三条铁律（沿用 + 更新）

1. **接口冻结**：`.h` 文件改动必须全组同步（组长①②会动 `Assembler.h`/`CPU.h`，队友动手前先 `git pull` 确认拿到最新）；
2. **每人一个 git 分支 + PR**：main 受分支规则保护（要求 PR + 1 approval + squash），**自己不能 approve 自己**——PR 找组长或任一队友点头；
3. **勤同步**：动手前 `git pull`，改完 push 开 PR；**骨架合入前别改核心文件**。
